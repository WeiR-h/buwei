## 重跑生产核心

安装 Python 3.12+、Rust 1.98.0 和本机 C 编译工具后，在源码目录运行：

```powershell
python tools/verify_portable_core.py --destination .run/core-check --output .run/core-result.json --benchmark-output .run/journal-benchmark.json
```

入口将实际使用的 `action-receipts` 和 `buwei-host-core` 原样复制到独立工作区，不需要账号、模型密钥或桌面依赖。依赖版本及摘要与桌面锁文件一致；测试和基准使用离线模式。每次选择新的检查目录，保留原结果。

[Windows/Linux 自动复验](../.github/workflows/portable-core.yml)逐平台保存测试数量、源码清单及摘要。覆盖授权、过期、账号隔离、重复执行、恢复、容量、同行整组、日期、偏好与意图更正。

## 实际耗时与历史恢复

设置页显示当前账号会话的处理耗时，使用单调时钟，统计各功能最近 128 次的中位数、95% 耗时及失败次数。切换账号或撤销授权后清空，退出后不保留。测量包含网络等待，不记录账号、房间、消息或需求原文。

回执基准分别使用混合账号和单一账号的 50,008 条合成历史记录，对比索引升级前后的生产查询，核对返回操作编号一致。单一账号场景有 50,005 条已核验历史结果和 3 条待核实操作。报告注明相同的开发编译配置，属于本地数据库基准；网络、模型和桌面渲染另行测量。

## 真实双账号与服务端证据

`tools/multi_role_acceptance.py` 使用本人提供的两个独立、已登录的本机资料，在两个账号分别拥有的已核验活动上，双向完成五轮报名、规则邀请、接受、名单导出与取消。成员导出他人名单、把私密活动发布为公开等操作必须被拒绝。活动新建另行记录，回归可复用既有活动。

从 Windows CI 的 `windows-acceptance` 工件取得单独启用的验收程序及构建证明，放入配套运行目录。普通发布程序不接受验收指令。使用明确选定的 `#buwei-test-…` 合成测试大厅。参数说明：

```powershell
python tools/multi_role_acceptance.py --help
```

每项操作从服务端按原操作编号查询，核对发送者和唯一事件数量。服务器时间与本地采集时间分别保存。程序摘要、原生源码摘要、依赖锁摘要和本轮结果相互绑定；运行中内容变化则拒绝导出。

`tools/live_evidence.py` 通过字段白名单导出 40 项不同操作的不可逆编号摘要、事件数量、时间和命令耗时。拒绝和结果不明的操作计入统计。账号、房间、消息、登录资料、模型原文和私人路径保留在本机。

本机双账号记录标为受控联调。本次网络验证使用已有的本机代理，未修改系统代理设置。独立用户试用和评审实机验证分别记录。

中途停止后先沿原操作编号恢复核实，再在本人界面确认取消本次测试报名，使用新的结果目录重新验证。脚本不会自动覆盖或撤销已有报名。

## 桌面与连续演示

[完整 Windows 构建及新环境启动](../.github/workflows/windows.yml)保存正式程序的构建来源，在另一台干净的 CI Windows 运行器上从下载包启动；核对固定源码和依赖。
